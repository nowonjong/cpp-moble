# 현재 prototype의 C++ 교재 범위 검토

## 판단

현재 prototype을 계속 발전시키는 방향은 적절하다. 교재의 클래스·참조자·STL 실습을 스스로 할 수 있는 팀이라면 사전 검색, 규칙 검사, AI 후보 비교, 턴·점수·통계 처리는 구현 가능한 응용 범위다.

다만 현재 구현 전체가 교재 안에 들어가지는 않는다. UTF-8 처리, Windows 한글 입력, 파일 입출력 및 안전한 기록 교체에는 추가 학습이 필요하다. 내가 실행 안정성과 자동 검증까지 고려하면서 넣은 부분이다. 특히 2·5·6번의 전체 코드를 교재 예제와 같은 난이도라고 판단해서는 안 된다.

개별 팀원의 숙련도를 측정한 결과는 아니다. 아래 난이도는 교재의 예제를 직접 작성할 수 있다는 전제에서 판단했다.

map<char32_t, vector<string>>는 한 음절을 키로 여러 단어를 묶은 것이다. 예를 들어 '사'에 사과·사자·사전을 연결한다. map과 vector를 조합한 응용이며 별도의 고급 자료구조를 직접 구현한 것은 아니다.

현재 클래스 사이에는 직접 만든 상속 구조나 가상함수 계층이 없다. 각 객체가 다른 객체를 참조하고 함수를 호출하는 구조다. 템플릿도 주로 표준 라이브러리를 사용하는 형태다. 교재에 등장한다는 이유로 상속이나 직접 new/delete를 추가할 필요는 없다.

## 교재 밖이지만 짧게 보충해서 유지할 문법

확인한 교재에서는 아래 항목의 별도 설명을 찾지 못했다. 문법이 낯설다는 이유만으로 구조를 다시 만들 필요는 없다.

| 항목 | 현재 의미 | 권장 방향 |
|---|---|---|
| auto, 범위 기반 for | 자료형을 추론하거나 목록을 하나씩 순회 | 읽기 어려운 곳은 실제 타입·반복 대상을 설명하고, 필요한 곳만 풀어 쓰기 |
| enum class | 승패·턴·오류 상태에 이름을 붙인 타입 | 유지 권장. 숫자 코드보다 공통 약속을 확인하기 쉽다 |
| std::optional | 선택한 단어·힌트가 있을 수도, 없을 수도 있음을 표시 | 값 존재 확인과 값 사용법을 보충해서 유지 가능 |
| 중괄호 초기화, 멤버 기본값 | 구조체를 초기 상태로 만들거나 여러 필드를 한 번에 반환 | 한 줄에 여러 의미가 겹친 곳은 단계별로 풀어 쓰기 |
| explicit, static_cast, nullptr | 생성자 사용 제한, 명시적 형 변환, 빈 포인터 | 필요한 사용례 위주로 설명 |
| char32_t, U/u8 문자열 표기 | 한글 음절 코드와 UTF-8 문자열 표현 | 2번의 문자 처리 학습과 함께 설명 |
| random_device, mt19937, uniform_int_distribution | 난수 초기화와 후보 번호 선택 | 호출 방법을 이해하면 된다. 난수 알고리즘 자체를 새로 구현할 필요는 없다 |

const 참조와 생성자 초기화 목록은 교재에 나온다. 이 부분까지 전부 교재 밖 문법으로 분류하는 것은 부정확하다.

## 추가 학습 부담이 큰 실제 지점

### 1. 한글 처리

[Utf8Util.cpp](C:/TeamProject2/prototype/Utf8Util.cpp:3)는 한글 글자 수를 세는 것뿐 아니라 UTF-8 바이트를 해석하고 잘못된 인코딩까지 거른다. 비트 연산 기호를 아는 것과 UTF-8의 바이트 규칙을 설계하는 것은 다른 학습 범위다.

2번은 우선 단어 검사와 연결·중복 규칙을 자기 코드로 설명할 수 있어야 한다. 디코더는 입력·출력, 실패 조건, 바이트를 음절 코드로 바꾸는 원리를 별도로 공부하는 공통 보조 코드로 다루는 것이 현실적이다. 이유를 모른 채 단순한 문자열 인덱싱으로 바꾸면 한글 처리가 깨질 수 있다.

### 2. Windows 콘솔

[ConsoleUI.cpp](C:/TeamProject2/prototype/ConsoleUI.cpp:14)의 ReadConsoleW와 WideCharToMultiByte, [main.cpp](C:/TeamProject2/prototype/main.cpp:43)의 wmain 및 콘솔 설정은 운영체제 API 학습 범위다.

메뉴 출력·메뉴 선택과 난이도가 다르다. 입력 보조 함수의 역할을 명확히 설명하고, 필요하면 별도 파일로 옮겨 UI 흐름을 읽기 쉽게 만드는 것을 권한다. 이미 수정한 한글 입력 동작을 유지하면서 정리해야 한다.

### 3. 파일 읽기와 안전한 저장

현재 C++ 교재에서는 fstream, sstream, filesystem의 본격적인 설명을 확인하지 못했다.

- ifstream/ofstream: 파일에서 읽고 파일에 쓰기.
- getline/istringstream: 줄을 읽고 필드별로 해석하기.
- filesystem: 경로, 파일 존재, 백업, 이름 변경을 다루기.
- error_code와 스트림 상태: 실패 원인을 구분해 호출한 곳에 전달하기.

기본 입출력은 보충 학습으로 구현할 수 있다. 다만 [RecordManager.cpp](C:/TeamProject2/prototype/RecordManager.cpp:88)는 임시 파일에 저장한 뒤 기존 파일을 교체하고, 실패하면 원본과 메모리 기록을 보존한다. resetRecords에는 백업도 있다. 전체 난이도는 단순히 파일 한 줄을 저장하는 과제보다 높다.

안전 처리를 없애서 짧게 만들기보다는, 저장 과정을 작은 단계로 설명하고 보조 함수의 역할을 분명히 하는 편이 좋다.

### 4. 자동 테스트용 코드

[tests/Tests.cpp](C:/TeamProject2/prototype/tests/Tests.cpp:41)의 람다와 std::function은 테스트 실행기를 위한 코드다. 게임의 핵심 구현에는 사용하지 않는다.

팀은 테스트 실행법과 검증하는 규칙을 알아야 하지만, 테스트 실행기의 모든 문법을 게임 기능 구현의 선행 조건으로 삼을 필요는 없다. ConsoleUI에 입력·출력 스트림을 전달하는 구조도 자동 검사에 쓰이며, 일반 실행에서는 cin/cout을 전달한다.

## 이어서 발전시킬 때의 권고

- 역할별 클래스와 헤더 분리를 유지한다.
- 낯선 짧은 문법은 실제 사용례로 설명하고, 여러 작업을 한 줄에 쓴 부분부터 풀어 쓴다.
- UTF-8, Windows 입력, 안전 저장의 목적·입출력·실패 조건을 문서화한다.
- 사전 인덱스와 파일 손상 방지 동작은 가독성을 정리하면서 보존한다.
- optional을 bool와 출력 인수로 바꾸는 등의 반환형 변경은 관련 팀원과 호출부를 함께 맞춰야 한다. 우선은 현재 인터페이스를 유지하는 편이 낫다.
- 각 담당자가 자기 함수의 입력·반환값·변경하는 데이터·실패 처리를 설명하고 작은 요구 변경을 직접 반영할 수 있는지를 개발 준비의 기준으로 삼는다.

예를 들어 5번은 새 기록을 추가했을 때 통계가 어떻게 바뀌는지, 중단 판의 높은 점수를 왜 최고점에서 제외하는지, 저장 실패 시 기존 기록을 어떻게 지키는지를 설명할 수 있어야 한다.
